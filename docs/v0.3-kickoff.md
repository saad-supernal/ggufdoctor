# v0.3 kickoff — read the Ollama spike before designing anything

Spike: [`docs/research/2026-09-03-ollama-spike.md`](research/2026-09-03-ollama-spike.md)
(Ollama at commit `b79067b0`, 2026-09-03). It changes the v0.3 line in the spec.

## What the spike found

- **There is no Jinja→Go conversion to model.** Ollama matches a GGUF's Jinja template against
  37 hard-coded strings by Levenshtein distance (`template.Named`, cutoff below 100) and
  substitutes one of 19 curated Go templates. An unrecognised template is, since Ollama's
  "use llama-server exclusively" change (`9db4bdba`, 2026-05-29), rendered by llama.cpp's own
  Jinja engine — which is exactly the engine v0.2 already embeds. For 9 of the 10 vendored
  templates, **v0.2's X001/X002 already describe what Ollama does.**
- **Embedding Ollama's Go `template` package is possible but pointless.** It builds for
  `wasip1` and runs byte-identically under wasmtime 48, but weighs 10.6 MB (14.7× the entire
  llama.cpp engine) and all the logic that matters (the 37-string matcher) is trivial to
  reimplement in Python: a bounded-Levenshtein selector reproduced Go's choice 10/10 in 96 ms
  for all ten templates. TinyGo cannot build `text/template`.
- **Only 1 of 10 vendored templates is recognised** (HyperCLOVAX → `chatml`). On it the
  comparison finds one real divergence (`tool_roundtrip`: Jinja2 raises, Ollama renders), one
  false positive to exclude (`no_generation_prompt` — Ollama has no `add_generation_prompt`),
  and one unrepresentable input (`api.Message.Content` is a `string`, so typed content cannot
  reach the Go template at all).

## What v0.3 should promise

X003 is re-posed: **"Ollama would swap this GGUF's template for its curated `<name>` Go
template, and that template renders differently."** It is a lookup-plus-render check, not an
engine.

| Item | Shape |
|---|---|
| Registry selection in pure Python | port of `template.Named` (37 strings + distances, vendored from the pinned Ollama commit with its licence) |
| Golden renders | 19 Go templates × the fixture corpus rendered once by real Go in CI and committed as data; the check compares the GGUF's Jinja render against the golden for the selected template |
| X003 | fires only when a template is recognised and the golden differs; reports the Ollama template name and the distance; `no_generation_prompt` and `typed_content` excluded by construction with the reason stated |
| Coverage line | "Ollama: would render this template with llama.cpp's engine (unrecognised)" for the 90% case — the honest and useful statement |
| `--runtime <ollama>` | shell out to a real `ollama` for ground truth; the only true oracle |
| Staleness guard | CI job that re-fetches Ollama's `template/index.json` at HEAD and fails when it differs from the vendored copy |

Do **not** build a WASM Ollama engine. The spec's §9 "Ollama Go conversion: vendored/ported
and compiled to WASM" is superseded by this spike; amend it the way the v0.2 amendments did.

## Biggest risk

Silent staleness: findings are valid only for the pinned Ollama commit. `index.json` has not
changed since 2025-03-20, but a new entry would make ggufdoctor under-report. The staleness
CI job above is the mitigation and belongs in the first task.

## Deferred from v0.2 (backlog for the v0.3 plan)

From `docs/process/v0.2/ledger.md`, the "may ship" minors: the fuel/memory headroom test
renders only the longest vendored template and its glob matches `*.upstream.jinja`;
`CORPUS_VERSION` is a constant while a `--fixtures` corpus carries its own `version` field
(read it); the `add_generation_prompt`-presence fork deserves a README note; a fixture with
assistant `reasoning_content` would exercise the `preserve_reasoning` branches (LiquidAI);
the null-content coercion has no explanation class (its two ERRORs are argued true positives);
legacy real-template tests in `test_checks_sanity.py` assert `(id, severity)` without fixtures.
