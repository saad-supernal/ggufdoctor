## The one design question that decides everything: how minja gets into Python

minja is header-only C++ inside llama.cpp (`common/minja/`). The spec says "C++
compiled to WASM, shipped in the wheel." Nobody has verified that is the best route,
and it should be settled by a **spike, not a plan**. The options, honestly:

1. **WASM via a Python WASM runtime** (`wasmtime` or `wasmer` pip package). One
   pure-Python wheel for every platform; the `.wasm` blob is data like `corpus.json`.
   Cost: a new runtime dependency (~10–30 MB), a WASI toolchain in the build, and a
   thin C shim exposing `render(template, json_context) -> (text | error)` across the
   boundary. This is what the spec assumes.
2. **Native extension** (nanobind/pybind11 + cibuildwheel). No runtime dependency,
   fastest. Cost: per-platform wheels (linux x86/arm, macOS, Windows × 3 Pythons), a
   C++ build in CI, and the classic "wheel missing for your platform" issue class —
   exactly the maintenance surface Saad said is the real constraint.
3. **Subprocess to a real llama.cpp binary.** Zero build complexity, strictly most
   truthful. Cost: the user must have llama.cpp. This is the spec's `--runtime` mode
   (v0.3) and is not a substitute for a bundled engine, but it is the **oracle the
   conformance suite needs**, so it gets built regardless.

**Done — see the spike doc.** Option 1 won; the spike text that follows is kept for the record.
**Original recommended first action:** a bounded spike (brainstorming skill, "spike" path).
Compile minja + a shim with wasi-sdk, run it under `wasmtime` from Python, render all
seven fixtures against a real template, measure blob size and cold-start time. Two
questions the spike must answer: does minja build cleanly for wasm32-wasi (it uses
`std::regex`, exceptions, and `<chrono>` — each a known WASI pain point), and is
`wasmtime`'s wheel footprint acceptable. If either answer is no, option 2 is the
fallback and the spec's §9 wording gets amended, with a ruling recorded.

Do not add a runtime dependency to `pyproject.toml` before the spike concludes. The
v0.1 "Jinja2 only" constraint was v0.1's; v0.2 is expected to add one, but which one is
the spike's output.

## Second question: what minja *is* in v0.2

minja tracks llama.cpp and changes. The engine's `.version` must name the llama.cpp
commit it was built from, every report prints it (spec §9), and the conformance suite
pins the same commit for its oracle. Decide in the spec how often to bump and who
bumps — this is the "Ollama's conversion can drift" risk from spec §11 applied to
minja too.

For the oracle: `llama-cpp-python` ships wheels and exposes template application; verify
whether its bundled llama.cpp exposes minja rendering with the same fixture context
before assuming it can serve as the CI oracle. If not, download a pinned llama.cpp
release binary in CI and drive `llama-cli`/`llama-server`.

## A correction to the deferred-items note

The v0.1 plan says vendored real templates should "reuse templates already captured in
`docs/research/2026-08-31-survey-raw.json`." **That file does not contain template
text** — records carry `id, org, downloads, status, diff_fixtures, diff_detail,
render_errors, arch, base_model, identical_source`. Neither does
`2026-09-01-survey.json` (`id, org, downloads, status, fixtures`). Vendoring therefore
needs a fetch step. Two reasonable shapes: a `--save-templates DIR` option on `survey`
that writes each compared template pair to disk (useful to users too — it turns the
survey into a corpus builder), or a one-off script under `docs/research/`. Prefer the
first; it is user-facing value, not just test plumbing. Keep vendored templates under
a directory that states their source repo, commit, and licence status — model repos
carry licences and some are gated.

The four real templates already vendored in `tests/test_checks_sanity.py` (Mistral-v0.2,
Llama-2-chat, Gemma-2, Llama-3.3-tools) are the seed. Note from the final review: the
Mistral and Llama-2 strings there are historical versions, not byte-identical to what
those repos publish today; their finding sets were verified equivalent, but a vendoring
step should record the exact source commit.

## Things the X family must not repeat

Every one of these happened in v0.1 and is written up in `NEXT-SESSION.md` and
`docs/process/v0.1/ledger.md` (rulings E1–E28):

- **Both engines get identical context, including the model's real tokens.** R001 was
  fixed to inject real `bos_token`/`eos_token` on both sides; the survey path still
  renders with placeholders (symmetric, documented). X checks compare two *engines* on
  the *same* template, so placeholder symmetry holds — but confirm it by construction
  in the review, as was done for R001.
- **An engine's error is not a template's defect.** X002 ("renders under Jinja2,
  fails under minja") is a finding about minja's subset, and its message must say so.
  A template using a Jinja2 feature minja lacks is a real user-facing problem (llama.cpp
  will fail on it) — that is the point of X002 — but the tool must not call the
  template "broken".
- **Whitespace-only goes to X004, never X001 ERROR.** Same discipline as R001's INFO split.
  (Ruling R7, 2026-09-03: a divergence the llama.cpp normaliser explains is classified first,
  as X001 INFO, even when the remaining difference is whitespace-only — cause outranks magnitude.)
- **Assert complete finding sets on real templates**, with genuine metadata. Never a
  test scoped to one id.
- **Record every skip.** If minja is unavailable (spike fallback, unsupported platform),
  `checks_not_evaluated` must carry X001/X002/X004/X005 and the headline must say
  "partial", following the "declined vs failed" distinction already in `report/human.py`.
- **Tool-calling first.** Fixture `with_tools` is where 5 of 16 real divergences live;
  the conformance suite and the X tests should lead with it.

## Process

Same as v0.1, and it is what caught eleven plan defects before they shipped:
`superpowers:brainstorming` (spike first, then architectural path) → spec section
amendments committed → `superpowers:writing-plans` → `superpowers:subagent-driven-development`
with a per-task two-verdict review and a whole-branch review at the end. The ledger
lives at `.superpowers/sdd/<plan-basename>/progress.md` (git-ignored — copy it into
`docs/process/v0.2/` when done, as was done for v0.1).

Work on a branch (`feat/v0.2`), merge to `main` only when the whole-branch review is
clean. `main` is what CI and the world see.
