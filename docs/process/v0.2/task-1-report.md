  the pinned commit; `--write-sums` regenerates `engine/llamacpp-sources.sha256`, otherwise

  ggml.
- `engine/shim.cpp` — reactor-style WASM shim: lex -> parse -> `caps_get` -> normalise
  messages (ported `messages_inp_normalizer`) -> render at pinned clock
  (`PINNED_NOW = 1767225600`, i.e. 2026-01-01T00:00:00Z). Exports `gd_alloc`, `gd_free`,
  `gd_render`, `gd_out_len`; never lets a C++ exception escape `gd_render`.
- `engine/build.sh` — compiles the module with wasi-sdk 34's `clang++`
  (`--target=wasm32-wasip1 -mexec-model=reactor -std=c++17 -Oz -fwasm-exceptions
  -mllvm -wasm-use-legacy-eh=false -Wl,-mllvm,-wasm-use-legacy-eh=false -Wl,--strip-all`,
  linked against `-lunwind` and the EH sysroot lib dir); downloads wasi-sdk into
  `engine/build/` when `WASI_SDK` is unset; writes the manifest via an inline Python
  heredoc.
- `src/ggufdoctor/engine_data/__init__.py` — empty, makes the data dir a package for
  `importlib.resources`.
- `src/ggufdoctor/engine_data/llamacpp-jinja.wasm` — the built module.
- `src/ggufdoctor/engine_data/llamacpp-jinja.json` — the manifest.
- `.gitignore` — added `engine/build/`.
- `tests/test_engine_data.py` — the two tests from the brief, verbatim.

Every hand-authored file (`shim.cpp`, `build.sh`, `fetch-llamacpp.sh`, `ggml-stub.h`) was

Using the spike's existing venv (`wasmtime` already installed there), I wrote a throwaway
driver at `/private/tmp/claude-501/.../scratchpad/smoke_reactor.py` that calls the reactor
exports directly (`gd_alloc`/`gd_render`/`gd_free`/`gd_out_len` through linear memory,

driver, since this module is a reactor, not a command). Results:

  `error: "Unknown statement: raise_exception"` — confirms the brief's documented "will not

This is throwaway scratch code, not committed, used only to build confidence beyond what the
two committed tests check (which only check the manifest and the raw bytes on disk, not
runtime behavior — that's Task 2's job).

## Concerns

- The module (721,494 bytes) is noticeably larger than the spike's 672 KB figure. This is
  expected — the spike shim only wrapped `ctx.current_time`; this shim adds
  `caps_get`/`caps::to_map`, the ~60-line message normaliser, and links `-lunwind` for real
  (the spike doc's 672 KB number was for a build that may not have needed the same code
  paths) — but it's worth Task 2/later tasks knowing the true baseline is ~721 KB, not
  ~672 KB, when budgeting future growth against the 1 MB ceiling.
- `build.sh`'s download-path branch (no `WASI_SDK` set) was not exercised end-to-end in this
  session — I used the pre-extracted SDK per the task's explicit guidance to avoid a 177 MB
  download. The script text is verified byte-identical to the brief's specification, so this
  is a low-risk gap, but it is not something I personally watched succeed.
- Upstream llama.cpp source emits two `-Wconstant-conversion` warnings per translation unit
  compiling `jinja/utils.h` (FNV-1a constants on a target where `size_t_digits` isn't 64).
  These are pre-existing in the pinned llama.cpp source, harmless (the ternary picks the
  32-bit constant branch correctly at runtime), and out of scope to fix since the brief says
  fetch-and-build the pinned sources as-is.
